# 数据库生产化与多租户改造方案

日期：2026-06-02  
适用产品：数字人直播带货中控系统  
文档性质：设计方案，不修改 `schema.sql`，不迁移数据，不重写全部表。  
商业模式背景：私有化买断优先，后续扩展 SaaS 订阅，需要提前规划多租户隔离。

## 0. 结论摘要

当前 SQLite + `schema.sql` 适合本地原型、单机演示和私有化买断早期交付，但不适合作为后续 SaaS 多租户、权限隔离、审计、并发写入和长期运营数据库底座。

推荐路线：

1. 短期：私有化单机阶段可暂留 SQLite，继续保证 `npm run server:seed`、`npm run server:smoke`、`npm run build` 通过。
2. 中期：引入轻量 migration 机制，先做“可回滚、可追踪”的版本化 schema，不直接一次性重写全部表。
3. 生产化：迁 PostgreSQL，使用 `timestamptz`、外键、事务、索引、`jsonb`、Row Level Security（RLS）和备份恢复能力。
4. 多租户：SaaS 推荐“共享库 + tenant_id 行级隔离 + PostgreSQL RLS”。私有化买断默认单租户，可用固定 `tenant_id = default` 兼容未来迁移。

## 1. 数据库选型结论

### 1.1 为什么从 SQLite 迁 PostgreSQL

| 维度 | SQLite 当前优势 | SQLite 生产风险 | PostgreSQL 优势 |
| --- | --- | --- | --- |
| 本地开发 | 零配置，seed 快，适合原型 | 与生产能力差异会越来越大 | 可通过 Docker / 托管服务保持生产一致性 |
| 并发写入 | 单机低并发够用 | 心跳、弹幕、日志、AI 调用日志会产生高频写入，单写锁容易成为瓶颈 | 多连接并发、事务隔离、连接池成熟 |
| 多租户 | 只能靠应用层过滤 | 一旦漏加条件，容易跨租户泄露 | 支持 RLS，可在数据库层强制租户隔离 |
| 数据完整性 | 当前基本无外键 | 依赖应用代码，容易出现孤儿数据 | 外键、CHECK、UNIQUE、部分索引、复合索引更完善 |
| JSON | TEXT 存储 | 不能高效查询和索引 JSON 内部字段 | `jsonb` 可索引、可查询、可局部更新 |
| 时间类型 | 当前多为 TEXT | 时区、排序、格式一致性依赖代码 | `timestamptz` 适合跨时区和审计 |
| 审计与恢复 | 文件级备份简单 | 大库备份、增量恢复、灾备能力弱 | WAL、逻辑备份、PITR、复制能力成熟 |
| 权限治理 | 主要靠应用 | 无数据库层隔离策略 | 角色、schema、RLS、审计扩展更完善 |

### 1.2 私有化单机阶段是否可暂留 SQLite

可以暂留，但前提是把它定位为“单机轻量交付 / PoC / 早期私有化”，而不是长期 SaaS 底座。

可暂留 SQLite 的条件：

- 单客户单租户部署。
- 不需要多个企业共享同一数据库。
- 并发运营人数较少。
- 弹幕、心跳、操作日志、AI 调用日志的数据量可控。
- 不要求数据库层 RLS。
- 允许通过文件备份做恢复。
- 部署环境不方便维护 PostgreSQL。

### 1.3 何时必须迁 PostgreSQL

满足任一条件，建议进入 PostgreSQL 迁移：

1. 开始做 SaaS 订阅，多个客户共用后端或数据库。
2. 需要数据库层防跨租户泄露。
3. 弹幕、心跳、AI 调用日志、操作日志等写入量明显增长。
4. 需要正式外键约束、事务一致性和审计追踪。
5. 需要稳定备份、恢复、复制、高可用或运维监控。
6. 需要基于 JSON 字段做查询、筛选、统计和索引。
7. 需要线上灰度、回滚、版本化 migration。
8. 执行端数量增加，心跳和命令表开始高频写入。
9. 需要把私有化版本和 SaaS 版本统一在同一套后端代码上。

## 2. 现有 Schema 问题清单与修订建议

当前 `server/db/schema.sql` 已有 43 张表。整体问题不是“表不够”，而是原型阶段为了快速落地，采用了较多：

- `TEXT` 时间字段。
- `REAL` 金额字段。
- JSON 字符串反范式字段。
- 冗余名称字段。
- 无显式外键约束。
- 缺少多租户隔离字段。

### 2.1 金额字段：REAL 改整数分或 numeric

当前发现字段：

| 表 | 字段 | 当前类型 | 问题 | 建议 |
| --- | --- | --- | --- | --- |
| `products` | `price` | `REAL` | 浮点误差，不适合金额 | 私有化/电商人民币优先改为 `price_cents BIGINT` |
| `ai_model_providers` | `today_cost` | `REAL` | API 成本可能有小数精度 | 改为 `today_cost_micros BIGINT` 或 `numeric(18,6)` |
| `ai_call_logs` | `cost` | `REAL` | 单次调用费用可能非常小 | 改为 `cost_micros BIGINT` 或 `numeric(18,6)` |
| `ai_cost_daily` | `today_cost` | `REAL` | 汇总成本需精确 | 改为 `today_cost_micros BIGINT` 或 `numeric(18,6)` |
| `ai_cost_daily` | `month_cost` | `REAL` | 汇总成本需精确 | 改为 `month_cost_micros BIGINT` 或 `numeric(18,6)` |
| `ai_cost_daily` | `average_cost` | `REAL` | 平均值可保留高精度 | 改为 `average_cost_micros BIGINT` 或 `numeric(18,6)` |
| `ai_cost_daily` | `budget_settings_json` | TEXT JSON | 预算金额藏在 JSON，无法约束 | 拆为 `ai_budget_settings` 或独立列 `daily_budget_cents` / `monthly_budget_cents` |

注意：`ai_model_providers.temperature REAL` 不是金额字段，可以保留为 `double precision` 或 `numeric(4,3)`，不按金额处理。

迁移办法建议：

1. Expand：新增整数列，例如 `products.price_cents BIGINT`，先允许 NULL。
2. Backfill：`price_cents = round(price * 100)`。
3. 双写：应用层保存商品时同时写 `price` 和 `price_cents`。
4. 切读：前端/API 改读 `price_cents`，展示时除以 100。
5. Contract：确认无旧代码读 `price` 后删除旧 `REAL` 字段。

AI 成本建议使用两种策略之一：

- 若按人民币结算：`cost_cents BIGINT`。
- 若需要保留极小 API 成本：`cost_micros BIGINT`（百万分之一元）或 PostgreSQL `numeric(18,6)`。

### 2.4 冗余冗存字段处理

当前常见冗余字段：

- `products.group_name`
- `live_rooms.avatar_name`
- `live_rooms.product_group_name`
- `live_tasks.live_room_name`
- `live_tasks.executor_name`
- `live_tasks.avatar_name`
- `live_tasks.product_group_name`
- `comments.product_name`
- `questions.product_name`
- `manual_takeover_state.current_avatar_name`
- `manual_takeover_state.current_product_group_name`
- `delay_control_state.current_avatar_name`
- `delay_control_state.current_product_group_name`
- `speech_queue.product_name`
- `executor_obs_status.executor_name`
- `executor_heartbeats.executor_name`

处理原则：

1. 对可变主数据，`id` 是权威来源，`name` 不参与关联。
2. 对历史快照，保留名称但改名为 `_name_snapshot`，例如 `product_name_snapshot`。
3. 对运行态状态表，允许冗余展示名，但必须有对应 id。
4. 对日志/审计表，保留快照名是合理的，因为历史记录不应随主数据改名而变化。
5. API 返回时可以继续同时返回 `id + name`，但数据库关系以 id 为准。

建议：

- `live_tasks`、`speech_queue`、`comments`、`questions` 这类历史/事件数据可以保留快照字段。
- `live_rooms`、`products` 这类配置主表不应依赖冗余名称，应通过 JOIN 获取最新名称。
- 文档和 API 契约中明确：`xxxId` 是关联依据，`xxxName` 是显示快照或 JOIN 展示字段。

### 2.5 时间字段 TEXT 改 timestamptz

当前几乎所有时间字段使用 `TEXT`：

- `created_at`
- `updated_at`
- `last_heartbeat_at`
- `scheduled_start_time`
- `comment_time`
- `submitted_at`
- `checked_at`
- `expires_at`
- `locked_until`
- `executed_at`
- `acked_at`

PostgreSQL 生产建议：

- 全部改为 `timestamptz`。
- 存储使用 UTC。
- API 仍返回 ISO 8601 字符串。
- 前端按用户时区展示。

迁移办法：

1. 新增 `created_at_ts timestamptz` 等临时列。
2. 使用 `created_at::timestamptz` 或显式 `to_timestamp` 回填。
3. 对空字符串统一转 NULL。
4. 应用层双读/双写。
5. 切读新列。
6. 删除旧 TEXT 列并把新列改名。

注意：

- SQLite 阶段继续用 TEXT 兼容即可。
- PostgreSQL migration 中不要直接假设所有旧时间字符串格式合法，先做数据检查。

## 3. 多租户方案

### 3.1 三种方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 共享库 + `tenant_id` 行级隔离 | 成本低、运维简单、适合 SaaS MVP；可配合 PostgreSQL RLS | 所有查询必须租户过滤；设计不严会有泄露风险 | 推荐默认路线 |
| 独立 schema | 隔离更强，单租户迁移/备份更清晰 | migration 复杂，schema 数量多后运维成本增加 | 中大型客户或区域隔离 |
| 独立库 | 隔离最强，便于私有化、独立备份、独立性能 | 成本最高，升级、监控、连接池和运维复杂 | 大客户、强合规、买断私有化 |

推荐：

- SaaS MVP：共享库 + `tenant_id` + PostgreSQL RLS。
- 私有化买断：独立库或独立部署，仍保留 `tenant_id = default`，方便未来统一代码。
- 高价值客户：可升级为独立 schema 或独立库。

### 3.2 tenant_id 与 org_id 定义

- `tenant_id`：租户隔离边界，对应客户、企业或私有化实例。
- `org_id`：租户内部组织、团队或部门，可选。MVP 可先不做复杂组织树。

推荐：

1. 所有业务表新增 `tenant_id NOT NULL`。
2. 需要团队/部门权限的数据再新增 `org_id`。
3. API 层和数据库层都以 `tenant_id` 为强制过滤条件。

### 3.4 查询层如何强制租户过滤

必须同时做应用层和数据库层防护。

#### 应用层

1. 用户登录后 session 中包含 `tenant_id`。
2. 执行端 device token 解析后得到 `executor.tenant_id`。
3. 所有 service/repository 函数必须接收 `tenantId`。
4. 禁止页面 route 直接拼 SQL。
5. 禁止路由层随手 `db.prepare` 访问业务表；后续应集中到 repository。
6. 所有列表、详情、更新、删除都必须带 `WHERE tenant_id = @tenantId`。
7. 创建数据时由后端写入 `tenant_id`，不信任前端提交的 `tenantId`。

#### PostgreSQL RLS

建议为所有租户表启用：

```sql
ALTER TABLE products ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_products
ON products
USING (tenant_id = current_setting('app.tenant_id')::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
```

每个请求事务开始时：

```sql
SET LOCAL app.tenant_id = '<current tenant uuid>';
```

这样即使应用层漏了 `WHERE tenant_id`，数据库也会拒绝跨租户访问。

#### 索引策略

租户表的常用索引应把 `tenant_id` 放前面：

```sql
CREATE INDEX idx_products_tenant_status ON products(tenant_id, status);
CREATE INDEX idx_live_tasks_tenant_status ON live_tasks(tenant_id, status);
CREATE INDEX idx_comments_tenant_task_time ON comments(tenant_id, live_task_id, comment_time DESC);
CREATE INDEX idx_executor_heartbeats_tenant_executor_time ON executor_heartbeats(tenant_id, executor_id, created_at DESC);
```

## 4. 迁移机制

### 4.1 工具选择

候选：

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| SQL 版本文件 + 自研轻量 runner | 透明、易审查、不引入复杂 ORM | 需要自己维护版本表和回滚约定 |
| `node-pg-migrate` | Node 项目适配好，支持 up/down | 多一个依赖，需要规范生成和审查 |
| Knex migration | JS 生态成熟 | 若项目不使用 Knex 查询层，可能引入额外抽象 |

推荐：

- 第一阶段使用 SQL 版本文件，最低成本建立 migration 纪律。
- PostgreSQL 正式迁移时可引入 `node-pg-migrate`，但所有生成脚本必须人工审查。

### 4.2 建议目录结构

```text
server/
  db/
    schema.sql                  # SQLite 本地开发基线，短期保留
    migrations/
      sqlite/
        000001_baseline.sql
        000002_executor_protocol.sql
      postgres/
        000001_extensions.sql
        000002_core_baseline.sql
        000003_money_columns.sql
        000004_tenant_columns.sql
        000005_foreign_keys.sql
    migrate.js                  # 未来：按 DATABASE_URL 判断执行 SQLite 或 PostgreSQL migration
```

迁移版本表：

```sql
CREATE TABLE schema_migrations (
  version TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  applied_at timestamptz NOT NULL DEFAULT now()
);
```

### 4.3 从当前 schema.sql 到第一版 migration 的落地步骤

1. 冻结当前 `schema.sql`，不要继续无版本地直接追加生产表结构。
2. 生成 `000001_baseline.sql`，内容等价于当前 SQLite schema。
3. 记录当前阶段为 baseline，不对历史 SQLite 数据做破坏性迁移。
4. 新增 `schema_migrations` 表。
5. 后续所有结构变化写入 migration 文件。
6. 本地开发继续支持 `runSchema()`，但生产环境禁止直接运行裸 `schema.sql` 覆盖结构。
7. 为 PostgreSQL 新建 `postgres/000001_extensions.sql`，启用：
   - `pgcrypto`：生成 UUID。
   - 可选 `citext`：邮箱/用户名大小写无关。
8. PostgreSQL baseline 不必完全照搬 SQLite 类型，应在第一版就使用：
   - `uuid` 或稳定 `text` id。
   - `timestamptz`。
   - `jsonb`。
   - `bigint` / `numeric` 金额。
   - `boolean`。

### 4.4 SQLite 与 PostgreSQL 并存过渡策略

短期保留：

```text
SQLite：本地开发 / 单机私有化 PoC
PostgreSQL：生产 / SaaS / 多租户验证
```

服务层建议：

1. 抽象 `server/db/client.js`，按 `DATABASE_URL` 或 `DB_DRIVER` 选择 SQLite / PostgreSQL。
2. 路由不直接依赖 `better-sqlite3` 细节。
3. 新增 repository 层，把 SQL 集中管理。
4. Smoke Test 分两套：
   - `server:smoke:sqlite`
   - `server:smoke:pg`
5. 在 PostgreSQL smoke 通过前，不切生产。

## 5. 分阶段实施计划

每个阶段都应满足：

```text
npm run server:seed
npm run server:smoke
npm run build
```

### Phase DB-1：Migration 纪律建立

目标：
- 新增 migration 目录和 `schema_migrations`。
- 不改变业务表。
- 把当前 `schema.sql` 标记为 SQLite baseline。

验收：
- seed / smoke / build 不变。
- 新增 migration 文档和 runner 雏形。

### Phase DB-2：金额字段安全迁移

目标：
- 新增 `price_cents`、`cost_micros`、`budget_cents` 等新列。
- 旧字段继续保留。
- API 同时返回旧展示字段和新标准字段。

验收：
- 商品、AI 成本页面不变。
- Smoke 增加金额字段检查。

### Phase DB-3：时间字段标准化

目标：
- PostgreSQL 侧使用 `timestamptz`。
- SQLite 侧继续 TEXT，但 API 输出统一 ISO。
- 空字符串时间改为 NULL 策略。

验收：
- 列表排序、日志筛选、心跳排序不回退。

### Phase DB-4：外键与数据清洗

目标：
- 先补索引。
- 检查孤儿数据。
- 分批添加外键。

验收：
- seed 数据无孤儿记录。
- 删除/更新接口符合外键策略。

### Phase DB-5：多租户基础字段

目标：
- 新增 `tenants` 表。
- 所有业务表新增 `tenant_id`，先允许 NULL。
- seed 写入默认租户。
- 后端 session/device token 增加 `tenant_id`。

验收：
- 单租户功能不变。
- Smoke 使用默认租户通过。

### Phase DB-6：强制租户过滤

目标：
- repository 函数必须带 `tenantId`。
- 所有查询加 `tenant_id`。
- PostgreSQL 开启 RLS。

验收：
- 新增跨租户隔离 smoke：租户 A 不能读租户 B 数据。
- 执行端 device token 只能访问本租户 executor。

### Phase DB-7：JSON 字段拆分

目标：
- 先拆高价值关系：角色权限、商品组关系、AI 成本 breakdown、OBS 映射。
- 低价值展示 JSON 保留 `jsonb`。

验收：
- 权限、商品组、成本监控、Studio 输出页面功能不变。

### Phase DB-8：PostgreSQL 生产试运行

目标：
- 引入 PostgreSQL 连接配置。
- PostgreSQL seed / smoke 全量通过。
- 保留 SQLite 本地开发。

验收：
- `server:smoke:pg` 通过。
- `server:smoke:sqlite` 通过。
- CI 可选择数据库驱动。

### Phase DB-9：SaaS 隔离演练

目标：
- 创建两个测试租户。
- 同表写入同名商品/数字人/直播任务。
- 验证 API 和 RLS 都无法跨租户访问。

验收：
- 跨租户访问全部返回 403 或空结果。
- 操作日志记录租户上下文。

## 6. 风险与注意事项

1. 不建议直接把当前 43 张表一次性全部重写为 PostgreSQL DDL。
2. 不建议在没有 repository 层前贸然做多租户，因为路由里散落 SQL 会增加漏过滤风险。
3. 不建议立刻删除冗余 name 字段，应先明确哪些是历史快照。
4. 不建议把所有 JSON 都拆表，配置型和展示型 JSON 用 `jsonb` 更经济。
5. 多租户隔离必须同时有应用层过滤和数据库 RLS。
6. 私有化买断部署也应保留 `tenant_id`，否则未来 SaaS 迁移会返工。

## 7. 本版不实施的内容

- 不修改 `server/db/schema.sql`。
- 不修改 `server/db/database.js`。
- 不修改 `server/db/seed.js`。
- 不创建 migration 文件。
- 不创建 PostgreSQL 连接。
- 不迁移 SQLite 数据。
- 不改业务接口。

后续实施应拆成独立任务逐步完成。
