# 下一阶段开发建议

本文档用于 Phase 12.20 之后规划真实化开发。当前项目已经完成前端原型、Service 层、本地 Express API、SQLite、核心 API 和 Smoke Test。下一阶段建议从“安全基础”和“真实集成最小闭环”开始，不建议直接接大模型、OBS 或直播平台。

## Phase 12.20 复核结论

对照 `docs/人工联调验收清单.md` 和 `docs/当前系统能力边界.md`，当前路线图与 Phase 0-12.19 的实际状态基本一致：

- 已完成并应继续视为基础能力：前端后台原型、Service 层、本地 Express API、SQLite、核心 API、Dashboard / Auth / File 占位 API、API 错误态收口、76 项 Smoke Test。
- 仍未真实接入且不应误判为完成：真实登录、真实 RBAC、真实文件上传、真实 AI 模型调用、真实 OBS、真实执行端、WebSocket、直播平台弹幕、数字人训练、TTS、口型同步和真实推流。
- Dashboard / Auth / File 已经具备基础 API 占位，因此后续不再建议“补 API 占位”，而是进入“真实化设计与安全落地”。
- 系统设置中的用户、角色、基础设置、操作日志已有本地 API 读取；但用户新增、重置密码、角色权限持久化、通知发送仍是 Mock，不能归类为真实权限系统已完成。
- 下一阶段顺序建议保留“人工联调问题修复”在最前面，然后先冻结 Auth / RBAC 方案，再做真实登录。File 与 AI 都依赖 Auth，因此排在 Auth 之后更稳。

## 推荐优先级

### A. Auth 真实登录与权限系统

建议优先级：最高

目标：

- 实现真实登录。
- 引入后端鉴权中间件。
- 建立用户、角色、权限 key、菜单权限和操作权限的最小 RBAC。
- 前端根据当前用户权限控制菜单和关键按钮可见性。

前置条件：

- 明确登录方式：账号密码、本地管理员、还是第三方登录。
- 明确 token / session 策略。
- 明确密码存储策略，例如 bcrypt 哈希。
- 明确权限 key 与菜单、接口、按钮的映射。

主要风险：

- 登录和权限属于安全基础，一旦做错会影响后续所有真实接口。
- 前端不能保存敏感凭据。
- 后端必须统一鉴权，不应只靠前端隐藏按钮。

建议交付：

- `/api/auth/login` 真实校验。
- `/api/auth/logout` 注销。
- `/api/auth/me` 返回当前用户、角色、权限。
- 基础权限中间件。
- 用户管理和角色权限页面从 Mock 操作升级为真实 API。

阶段准入条件：

- `npm run server:smoke` 和 `npm run build` 在 `dev` 上通过。
- 已完成一轮人工联调，且没有阻塞级页面错误。
- 已冻结登录态方案：Session / Token 二选一，并明确过期、刷新和退出策略。
- 已冻结权限 key 与菜单、接口、按钮的映射。
- 已确认不会把任何密码、token、API Key 写入前端、docs 或 Mock。

### B. File 真实上传

建议优先级：高

当前状态：

- Phase 14 已完成本地文件上传 MVP。
- `POST /api/files/upload` 已支持 `multipart/form-data`、本地 `server/uploads` 保存、`file_assets` 记录、登录 token 校验、大小限制和类型限制。
- 商品主图已先接入真实本地上传。

后续目标：

- 保存商品图、数字人素材、工单截图、授权文件等。
- 将真实上传从商品主图扩展到数字人素材、工单截图、授权文件和系统 Logo。

前置条件：

- 明确本地存储目录和访问 URL。
- 明确文件大小限制。
- 明确允许的 mime type。
- 明确业务模块和文件类型映射。
- 登录鉴权最好先完成。

主要风险：

- 文件上传容易带来安全风险，如恶意文件、超大文件、路径穿越。
- 生产环境如果改为云存储，需要重新设计签名 URL 和访问权限。

建议交付：

- `multer` 或等价上传中间件。
- 本地上传目录加入 `.gitignore`。
- 文件类型和大小校验。
- `file_assets` 持久化。
- 商品主图、数字人素材、工单附件先小范围接入。

阶段准入条件：

- Auth / RBAC MVP 已经完成，至少能识别当前用户。
- 已明确本地上传目录、访问 URL、文件大小上限和允许的 mime type。
- 已确认上传目录、临时目录和生成文件全部加入 `.gitignore`。
- 已明确哪些页面先接真实上传，避免一次性改全站 Upload。
- 已准备失败态验收：超大文件、非法类型、缺少权限、存储失败。

### C. AI 模型后端代理

建议优先级：高

目标：

- 真实模型调用只能由后端代理。
- 前端不接触任何 API Key。
- 支持 Kimi / Mimo / OpenAI / DeepSeek 等服务商的安全配置。

前置条件：

- Auth 和权限最好先完成。
- 明确密钥存储方式：环境变量、系统密钥管理、或本地加密存储。
- 明确每个 AI 场景的 Prompt 模板、输入输出字段和合规规则。
- 明确调用限流、超时、重试和费用保护。

主要风险：

- API Key 泄露风险。
- 费用失控风险。
- Prompt 和返回内容可能包含敏感信息。
- 模型返回不稳定，需要前后端容错。

建议交付：

- `PUT /api/ai/models/:id/credentials` 真实密钥配置接口。
- `POST /api/ai/models/:id/test` 后端代理测试。
- 商品文案或弹幕回复选择一个低风险场景先试点。
- 调用日志脱敏。
- 费用和频率限制。

阶段准入条件：

- Auth / RBAC MVP 已完成，且只有授权角色可配置模型。
- 已明确密钥来源和存储方式，前端仅展示脱敏状态。
- 已明确首个试点场景，建议从商品文案或弹幕回复二选一。
- 已设置超时、频率限制、费用上限和脱敏日志规则。
- 已准备模型不可用、超时、余额不足、返回格式异常的前端错误态。

### D. OBS / 执行端通信

建议优先级：中高

目标：

- 建立云端后台与本地执行端的真实通信方式。
- 执行端负责 OBS、虚拟摄像头、数字人画面和本地任务执行。

前置条件：

- 明确执行端技术栈：Electron、Tauri、Python、Node CLI 或其他。
- 明确执行端注册、绑定、认证方式。
- 明确通信协议：HTTP 轮询、WebSocket、局域网直连或云端中继。
- 明确 OBS WebSocket 版本和连接安全策略。

主要风险：

- 执行端是真实系统复杂度最高的部分之一。
- OBS 场景、来源、窗口捕获在不同电脑上差异大。
- 网络断连、执行端离线、权限不足都需要容错。

建议交付：

- 执行端最小程序。
- 绑定码真实绑定。
- 心跳上报。
- 命令下发和状态回执。
- OBS 只先实现测试连接和读取场景，不直接做复杂播控。

阶段准入条件：

- Auth / RBAC MVP 已完成，执行端绑定和命令下发有权限控制。
- 已确定执行端技术栈和运行平台。
- 已确定执行端注册、绑定、解绑和刷新配置协议。
- 已确定命令下发的幂等、超时、重试和回执格式。
- 已明确本阶段只做最小通信闭环，不做复杂 OBS 自动播控。

### E. WebSocket 实时弹幕和心跳

建议优先级：中

目标：

- 建立实时通道，用于弹幕流、执行端心跳、直播中控台状态更新。

前置条件：

- Auth 基础完成。
- 明确 WebSocket 鉴权方式。
- 明确消息类型和数据契约。
- 先有执行端或弹幕输入源的最小真实数据。

主要风险：

- 实时消息容易产生状态同步问题。
- 断线重连、消息重复、消息顺序和消息积压都需要处理。
- 如果直接接直播平台弹幕，还会引入平台接口和合规风险。

建议交付：

- 后端 WebSocket 网关。
- 前端统一实时连接工具。
- 执行端心跳或模拟弹幕先做一个真实流试点。
- 直播中控台只消费聚合后的实时状态，不直接耦合多个原始通道。

阶段准入条件：

- Auth / RBAC MVP 已完成，并明确 WebSocket 鉴权方式。
- 至少有一个真实或半真实数据源，例如执行端心跳或内部模拟弹幕流。
- 已定义消息类型、消息 id、时间戳、重连和去重策略。
- 已定义前端断线重连、降级轮询和错误提示。
- 已确认不直接接入直播平台弹幕，除非平台鉴权和合规方案已准备好。

### F. 前端 UI / 动效优化

建议优先级：中低

目标：

- 在功能链路稳定后，提高可用性和一致性。
- 优化大屏中控台、表格密度、错误态、空状态、筛选区和表单体验。

前置条件：

- 主要 API 链路稳定。
- 明确真实用户角色和日常操作路径。
- 完成一轮人工联调验收。

主要风险：

- 过早做 UI 大改会和真实 API 联调互相干扰。
- 动效不能影响后台操作效率。

建议交付：

- 统一 PageHeader、FilterBar、Table 操作风格。
- 直播中控台做 1920x1080 专项布局优化。
- 大模块按需 code splitting，降低当前 Vite chunk 体积提醒。
- 针对高频操作增加快捷反馈和确认机制。

阶段准入条件：

- 人工联调已完成，且高频页面路径明确。
- 真实 API 链路没有阻塞级错误。
- 已列出需要统一的组件范围，避免大规模无边界重构。
- 已确认 UI 优化不改变业务语义和接口契约。
- 如果处理 chunk 体积，需要先确定路由级分包策略。

### G. 云端部署

建议优先级：后置

目标：

- 将本地原型逐步升级为可部署环境。
- 明确前端、后端、数据库、文件存储和执行端通信的部署方式。

前置条件：

- Auth、文件、AI 代理、安全策略至少完成 MVP。
- 明确部署目标：本地私有化、云服务器、容器化、或内网部署。
- 明确日志、备份、监控和升级策略。

主要风险：

- SQLite 适合本地和原型，不一定适合多用户生产场景。
- 生产环境需要 HTTPS、密钥管理、日志脱敏、备份恢复和权限隔离。
- 执行端和云端之间的网络环境复杂。

建议交付：

- `.env.example` 完善。
- Dockerfile / docker-compose 草案。
- 数据库迁移方案。
- 部署 README。
- 生产安全检查清单。

阶段准入条件：

- Auth、File、AI 代理至少完成 MVP。
- 已明确部署形态：本地私有化、云服务器、容器化或内网部署。
- 已明确密钥管理、HTTPS、日志脱敏、备份恢复和数据库迁移方案。
- 已明确 SQLite 是否继续使用；如切换数据库，需要先完成迁移设计。
- 已完成一轮 smoke test、build 和关键页面人工验收。

## 换电脑继续开发说明

在新电脑上继续开发时，按以下步骤：

```bash
git clone https://github.com/XXFH1277/szr-live-new.git
cd szr-live-new
git checkout dev
npm install
npm run server:seed
npm run server:dev
```

另开终端：

```bash
npm run dev
```

联调和构建检查：

```bash
npm run server:smoke
npm run build
```

如果需要新功能分支：

```bash
git checkout dev
git pull origin dev
git checkout -b feature/your-feature-name
```

## 安全提醒

不要提交：

- `.env.local`
- `模型api.txt`
- `server/data/*.sqlite`
- `server/data/*.db`
- 真实客户文件
- 真实用户手机号、邮箱、IP
- 真实 API Key

不要把 API Key 写进：

- 前端代码
- `src/mock`
- `docs`
- `04_AI开发交接记录.md`
- `VITE_` 环境变量

特别注意：

```text
VITE_ 变量会被打包进浏览器 bundle，不能放模型 Key。
```

真实密钥后续只能由后端读取，并且需要脱敏、权限控制、日志保护、频率限制和费用保护。

## 推荐当前验收方式

1. 先运行 `npm run server:seed` 保证数据干净。
2. 启动后端和前端。
3. 按 `docs/人工联调验收清单.md` 逐模块点击。
4. 发现问题按“模块 / 页面 / 操作 / 预期 / 实际 / 截图 / 控制台错误”记录。
5. 每轮修复后运行 `npm run server:smoke` 和 `npm run build`。
