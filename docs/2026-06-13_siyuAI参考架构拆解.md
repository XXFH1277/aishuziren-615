## 3. 目录分层观察

siyuAI 的结构大致分为：

```text
api/      对外或内部 API 封装，主要为 .pyd
bin/      模型推理与训练/转换相关模块
live/     直播编排、克隆管理、声音直播管理
tools/    弹幕、LLM、违禁词、音频处理、自动直播动作等业务工具
assets/   预训练模型、虚拟摄像头插件、SRS、弹幕采集 WebView 等资源
env/      内置 Python / CUDA / PyTorch / ffmpeg / WebSocket / streamlit 等运行环境
config/   全局配置
```

这说明它不是单一“数字人模型”，而是一个本地一体化运行时：

```text
配置层
  ↓
语言/弹幕/合规工具层
  ↓
声音生成/声音克隆层
  ↓
口型/图像推理层
  ↓
直播编排层
  ↓
虚拟摄像头 / RTMP / SRS / OBS 捕获
```

## 4. 全局配置方式

`config/config.yaml` 不是只配置 LLM，而是集中管理多类能力。

### 4.1 运行参数

观察到的非密钥字段：

```text
device = cuda
batch_size = 4
use_fp16 = true
is_half = false
window_width = 720
window_height = 1280
```

含义：

- 默认按 GPU / CUDA 运行。
- 面向竖屏直播间，画布为 720×1280。
- 推理使用半精度相关配置，但不同模块可能分别控制 `use_fp16` 与 `is_half`。

### 4.2 LLM 配置

观察到的非密钥字段：

```text
llm_config.vendor = volcengine
llm_config.endpoint = https://ark.cn-beijing.volces.com/api/v3/chat/completions
llm_config.model = doubao-seed-1-6-250615
```

脱敏字段：

```text
llm_config.api_key = [REDACTED]
```

判断：

- 语言层接的是火山方舟 OpenAI-compatible Chat Completions 接口。
- 当前模型是豆包系模型。
- 配置方式与我们 AI 能力中心现有 `provider/baseUrl/modelName/credentialRef` 方向一致。

### 4.3 语音/公告配置

观察到：

```text
video_announcement.provider = aliyun
video_announcement.sync_lip_enabled = true
voice_llm_config.group_id = ''
```

脱敏字段：

```text
video_announcement.aliyun.api_key = [REDACTED]
video_announcement.minimax.api_key = [REDACTED]
voice_llm_config.api_key = [REDACTED]
```

判断：

- 视频公告可能支持阿里云 / MiniMax 等云端语音或视频能力。
- `sync_lip_enabled` 表示公告视频链路中显式配置口型同步。
- 语音侧还有独立的 `voice_llm_config`，说明“直播问答 LLM”和“语音/公告生成”可能是分开的。

判断：

- `Hubert`、`Chinese Roberta`、`BigVGAN`、`HiFiGAN`、`RMVPE` 等命名表明它包含音色特征、声码器、F0/音高等组件。
- 我们系统不应直接绑定某一个具体 TTS；应抽象为 `VoiceEngineAdapter`。

建议抽象：

```text

- getVoices()
- getStatus()
```

## 7. OBS / 输出链路参考

### 7.1 虚拟摄像头插件

观察到：

```text
assets/plugin/camera/obs-virtualcam-module32.dll
assets/plugin/camera/obs-virtualcam-module64.dll
assets/plugin/camera/virtualcam-install.bat
assets/plugin/camera/virtualcam-uninstall.bat
```

安装脚本行为：

- 通过 `regsvr32` 注册 32/64 位 OBS VirtualCam DirectShow DLL。
- 注册 CLSID：

```text
{A3FCE0F5-3493-419F-958A-ABA1250EC20B}
```

- 将 FriendlyName 写成：

```text
C920
```

判断：

- 它不是只通过 OBS WebSocket 控制 OBS。
- 它把数字人画面输出为一个系统级虚拟摄像头，让 OBS / 直播伴侣 / 平台客户端像采集真实摄像头一样采集它。
- `C920` 这个命名是在模拟常见 Logitech 摄像头名称，降低平台识别/选择成本。

对我们启发：

- 当前我们已接 OBS WebSocket 读状态/场景，这是“控制 OBS”路线。
- 但真实数字人画面输出更应该补“虚拟摄像头输出路线”。
- 私有化场景建议支持两种输出：

```text
路线 A：数字人窗口/画面 → OBS 窗口捕获 / 浏览器源
路线 B：数字人画面 → 虚拟摄像头 → OBS/直播伴侣采集
路线 C：数字人画面 → RTMP/SRS → OBS 媒体源/平台推流
```

- 这说明其画面输出不只依赖虚拟摄像头，也可能支持本地流媒体转发。

对我们启发：

- 执行端应增加“输出目标 OutputTarget”概念：


## 10. 对当前系统的下一步建议

### 10.1 不要直接接 siyuAI 私有端口

原因：

- `127.0.0.1:12345` 已确认不是普通 HTTP/OpenAPI/标准 WebSocket。
- 未确认协议前直接逆向或猜协议风险高。
- 可能涉及授权、license、账号态和软件内部协议。

建议：

- 继续把 siyuAI 当参考架构，不当依赖。
- 我们自己的执行端继续走开放协议：HTTP/轮询命令 + adapter。

## 12. 结论

siyuAI 对当前项目最有价值的参考点不是某个接口，而是它的产品工程拆法：

```text
本地 CUDA 模型运行时
  + 声音克隆/TTS 多引擎
  + 音频特征驱动口型/画面
  + 弹幕/LLM/合规工具
  + 虚拟摄像头/RTMP/SRS 输出
```

我们的系统应继续保持：

```text
云端后台负责管理、审核、排队、合规、任务编排
本地执行端负责模型推理、OBS/虚拟摄像头/RTMP 和平台环境
```

下一步更合理的工作不是“接 siyuAI 端口”，而是把我们的执行端协议扩展成可承载上述能力的运行时配置与适配器体系。
